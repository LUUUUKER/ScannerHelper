# 架构变更：扫码枪改走虚拟串口 / Architecture change: the scanner moves to a virtual COM port

**状态 / Status:** 已采纳，2026-09-10 / Adopted, 2026-09-10
**取代 / Supersedes:** 规格 §4 全部、§5.3、§5.6 的一半、§6、§7 的一条规则、§19.1、§22.5 的结论
**依据 / Evidence:** `TASK_4B_FINDING_20260910.md`（失败），以及本文件 §2（成功）

> 本文件与规格冲突时**以本文件为准**，直到规格被改写。
> Where this document and the spec disagree, **this document governs** until the spec is rewritten.

---

## 1. 为什么必须变 / Why this had to change

规格 §5.3 的输入架构是：钩子先把按键吞掉 → 等 Raw Input 揭示是哪台设备 → 再决定
留还是补发。2026-09-10 的实测证明这条路走不通：

> **按键一旦被 `WH_KEYBOARD_LL` 吞掉，Windows 就不再为它产生 `WM_INPUT`。**

同一台机器、同一把枪、同一份代码，唯一变量是吞不吞：

| | 吞 | 不吞 |
|---|---:|---:|
| 来自绑定扫码枪的 Raw Input | **0** | ≈487 |
| 处理完成的扫描 | **0** | **10（全对）** |

**扣留这个动作本身，销毁了做决定所需要的证据。** 这不是实现缺陷——不吞的时候
配对是完美的，说明设备识别、身份定义、关联器、时间基准全都是对的。
在用户态里，Raw Input 知道是谁按的但拦不住，低层钩子拦得住但不知道是谁按的，
而**两者不能合用**。完整证据见 `TASK_4B_FINDING_20260910.md`。

---

## 2. 新方案的实测 / The new approach, measured

把扫码枪用配置条码切到 **USB 虚拟串口（CDC）** 模式后，2026-09-10 在
LAPTOP-AI4MH002 上实测：

| 项 | 结果 |
|---|---|
| 记事本里扫码 | **什么都不出现**——扫码枪不再打字 |
| 收到的帧 | 21 帧，全部 `ABCDEFG123456789` |
| 每帧长度 | 16，终止符 `CR` |
| 字节总数 | **357 = 21 × 17**，一个字节不多不少 |
| 读取错误 | 0 |
| 内容不符 | 0 |

**字节数的精确吻合是关键：** 21 枪 ×（16 字符 + 1 个 CR）= 357，说明这条链路上
既没有丢字符也没有多字符。而键盘模拟那条路，在**本程序完全不启动**时都会出错
（规格 §22.5，字符间隔中位数 1.1 毫秒）。

---

## 3. 决定 / The decision

> **扫码枪工作在 USB 虚拟串口模式。本程序从串口读取条码，业务软件永远收不到
> 扫码枪发出的任何东西。**
>
> **The scanner operates as a USB virtual COM device. This application reads barcodes from the
> port, and the business application never receives anything the scanner emits.**

「防止原文泄漏」不再是一件需要我们去做的事——它成了一个**结构上的事实**：
扫码枪根本不打字，没有什么可泄漏的。

## 4. 规格里哪些条款作废、哪些改写 / What this changes in the spec

| 规格段落 | 处置 |
|---|---|
| **§4 V1 Input Architecture**（全节） | **作废。** Raw Input + `WH_KEYBOARD_LL` + 事件关联的整套设计不再使用。§4.3 的 4a/4b spike 已完成使命：4a 的测量有效，4b 的结论是「此路不通」。 |
| **§5.3 IDENTIFYING** | **作废。** 不再有「来源未定」这个状态——串口来的数据，来源是确定的。 |
| **§5.1 状态机** | **改写。** IDLE → SCANNING → PROCESSING →（PENDING_ERROR）。去掉 IDENTIFYING。 |
| **§5.4 SCANNING** | **保留但简化。** 一帧的边界由串口终止符给出，不再需要按键级的超时拼装。 |
| **§5.6 合成输入安全** | **减半保留。** 我们自己的 `SendInput` 输出仍然要打标记，但不再有「被自己的钩子重新吃进去」的风险——因为不再有捕获用的钩子。（顺带：4b 证明了合成按键**会**产生 Raw Input，原注释里那句相反的假设是错的。） |
| **§6 设备绑定** | **改写。** 绑定的对象从「Raw Input 设备句柄 / 设备路径」变成「串口 + 该串口背后的 USB 设备（VID/PID/序列号）」。理由见 §6 新增风险。 |
| **§7 F8 只能由非扫码枪的物理键盘触发** | **不再需要，但规则保留。** 串口模式下扫码枪**发不出任何按键**，这条规则自动成立。实现上不再需要判断来源。 |
| **§10 输出契约** | **完全保留。** `SendInput` + `KEYEVENTF_UNICODE`、可选补回车，一字不改。 |
| **§8 / §9 解析与校验** | **完全保留。** 230 个单元用例不受影响。 |
| **§19.1 静默摘钩检测** | **形态改变，要求不变。** 不再有钩子可摘，但出现了新的静默失效（见 §5），因此「界面绝不显示一个它没有验证过的运行状态」这条原则原样适用。 |
| **§22.5 扫码枪丢字符** | **结论改写。** 那是键盘模拟通道的性质，串口模式下不复现（21 枪零误差）。 |
| **§16 / §17 结构** | **改写。** 见 §7。 |

## 5. 新的风险 / New risks — 必须正视

换方案消灭了一大类问题，但引入了三条新的，其中第一条最危险。

### 5.1 ★ 有人把枪切回键盘模式 —— 新的「看起来在工作」

扫一张配置条码就能把枪切回 USB 键盘模式。一旦发生：

- 本程序的串口再也收不到任何数据，**但它不会报错**——串口好好地开着，只是没数据；
- 而扫码枪开始**直接往业务软件里打字**，原始条码原封不动地进去了。

这正是规格 §19.1 描述的那类失效：程序还在跑、界面还显示着模式，而它要防的事
正在发生。**必须检测**：串口打开着但长时间无数据，界面就不能再显示一个笃定的
「正常」状态。这是新架构下心跳检测的形态。

### 5.2 端口号会变

换一个 USB 口，`COM3` 可能变成 `COM7`。因此**绑定不能只存端口号**，要连同该端口
背后的 USB 设备身份（VID/PID，有序列号更好）一起存，重连时按身份找端口。
这与规格 §6「优先用具体身份而不是 VID/PID」的精神一致，只是落到了另一层。

### 5.3 端口可能被别的程序占用

串口是独占的。别的程序（另一个本程序实例、串口调试助手、某些厂商工具）先打开了，
我们就打不开。错误信息必须原样呈现给使用者——「端口被占用」本身就是最有用的
线索。多开检测（规格 §14 单实例）因此变得更重要。

### 5.4 上线多了一步

每一把新枪都要扫一次配置条码。这是运维成本，不是技术风险，但必须写进部署文档，
并且配置条码要和程序一起发（打印一张贴在工位上）。

## 6. 消失了的问题 / What simply goes away

以下每一项在旧架构里都是需要专门设计、专门测试、专门防守的东西：

- 拦截与首字符泄漏
- 扣留—补发，以及它对**中文输入法组字**的破坏（规格 §4.3 的第 3 条硬性关卡）
- 修饰键、按住重复、CapsLock 经过补发之后的正确性
- `LowLevelHooksTimeout` 与钩子被 Windows 静默摘掉
- 钩子回调的时间预算（解析、正则、`SendInput` 都不能放进去）
- UIPI 导致钩子看不见按键
- 「扫码枪发出的 F8 会不会误切模式」
- 关联窗口、超时重放、事件顺序、两条通道的时间基准
- 规格 §22.5 的丢字符

以及一件很实际的事：**工人的键盘从头到尾没有被碰过**，因此「程序把键盘搞坏了」
这一整类现场事故不可能发生（规格假设 A4：笔记本工位没有备用键盘可插）。

## 7. 代码：留什么、删什么、加什么 / Code impact

### 保留（不动）

- `ScannerHelper.Core` 的解析、校验、模式、设置、输出契约——**230 个用例照常全绿**
- `SendInputKeyboardOutputService`、`InjectedInputTag`、`DeferredKeyboardOutput`
- 全部界面与本地化工作（尚未开始的部分）

### 删除

| 文件 | 理由 |
|---|---|
| `InputEventCorrelator` / `IInputEventCorrelator` / `CorrelationDecision` / `CorrelationOutcome` | 不再有两条通道要关联 |
| `KeyEvent` / `RawInputEvent` / `KeyIdentity` | 按键级的领域类型不再需要（热键除外，见下） |
| `LowLevelKeyboardHook`（捕获用途）/ `KeystrokeReplayService` / `KeyboardCharacterDecoder` | 不再拦截、不再补发、不再解码扫描码 |
| `RawInputKeyboardListener` / `RawInputDeviceResolver` / `Win32ScannerInputSource` | 扫码枪不再是键盘设备 |
| `DeviceIdentityMatcher` 的 Raw Input 部分 | 匹配对象换成串口背后的 USB 设备 |
| `ScanSession` 的按键级拼装 | 帧边界由串口终止符给出 |

诊断工具的 4a / 4b 窗口**保留但冻结**：它们是这次结论的证据，删掉就等于把
「为什么换方案」的依据一起删掉了。

### 新增

| 文件 | 职责 |
|---|---|
| `Serial/SerialScannerReader`（已完成） | 开端口、读字节、按终止符切帧 |
| `Serial/SerialPortResolver` | 端口 ↔ USB 设备身份（VID/PID/序列号），供绑定与重连 |
| `SerialScannerInputSource` | 实现 Core 的 `IScannerInputSource`，把帧变成一次扫描 |
| `Core/Input/IScannerInputSource` | Core 侧的抽象：一次扫描 = 一个完整的原始码 |
| 端口健康检测 | §5.1 那条新的静默失效 |

热键（F8 / F10 / Esc）仍然需要一个全局入口。**优先用 `RegisterHotKey` 而不是
低层钩子**：前者没有 `LowLevelHooksTimeout` 那一整类风险，而我们已经不需要
钩子做别的事了。Esc 若不适合注册为全局热键，则只在本程序有焦点时生效——
这一条留待热键任务定夺。

## 8. 待定的问题 / Open questions

### D-26：串口模式下 PAUSED 是什么意思？

旧的 PAUSED 是「键盘失灵时的救命稻草」：钩子放行一切。现在键盘从未被碰过，
那个意思不存在了。两个候选：

- **甲：暂停 = 不发送。** 扫码枪的内容读进来但不发给业务软件。语义干净，
  但工人在暂停期间**完全没法录入**。
- **乙：暂停 = 原样发送。** 跳过解析与校验，把原始码直接发出去。
  规则配错时仍然能干活，更接近旧 PAUSED「出问题时还能工作」的本意。

倾向乙，但这是业务决定，需要确认。

### D-27：串口参数要不要做成设置项？

波特率、终止符在扫码枪那边是可配置的。实测这把枪是 9600 / CR。做成设置项能
适配不同的枪，代价是多两个用户看不懂的选项。倾向做成设置但给出正确的默认值，
并在诊断页显示实测到的终止符。
