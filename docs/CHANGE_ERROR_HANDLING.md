# 规格变更：出错之后怎么办 / Spec change: what happens after a failed scan

> **日期 / Date:** 2026-09-15
> **状态：已实施。凡与 `SCANNER_HELPER_SPEC.md` 不一致处，以本文件为准。**
> **Status: in effect. Where this disagrees with `SCANNER_HELPER_SPEC.md`, this document governs.**

---

## 1. 一句话 / In one line

> **解析或校验没过的码，永远不进业务软件。**
> 界面告诉工人是在**哪个模式**下没过，给两个明确的模式按钮；工人换模式重扫即可。
> 强制发送（F10）与取消（Esc）**取消**。真正解析不了的码走**暂停**。

> A code that failed parsing or validation never reaches the business application. The screen says
> which mode it failed in and offers two explicit mode buttons; the operator switches and rescans.
> Force Send (F10) and Cancel (Escape) are gone. A genuinely unparseable code goes through PAUSED.

---

## 2. 为什么 / Why

### 2.1 强制发送是这套设计里最危险的一个功能

它的语义是：**规则判定这一枪不合格，但还是把原始码原样发进业务软件。**

偶尔按一次是救急。问题在于它会变成习惯——而习惯性使用意味着持续往仓库系统里灌
未解析的原始码。

**更要命的是事后查不出来。** 业务系统里那条记录和正常记录长得一模一样：没有标记、
没有前缀、没有任何痕迹说明它是绕过规则进去的。只有本程序的日志知道（`ForceSent`），
而对账的人手上未必有这份日志，也未必想得到要去要。

这正是规格 §19.1 反复在防的那一类：**一个看起来正常、实际已经错了的状态**。

### 2.2 去掉它并不损失能力

那条退路已经存在，而且形式更好：**暂停**。

工人点一下暂停 → 扫那个死活解析不了的码 → 点恢复。原文照样进业务软件。
和 F10 做的事**完全一样**，但：

| | F10 强制发送 | 暂停 |
|---|---|---|
| 工人看得见吗 | 按一下，屏幕闪一下就过去了 | 界面整片变灰，写着「已暂停」，直到他自己恢复 |
| 鼠标能做吗 | 界面上有按钮，但主要是快捷键 | 规格 §5.7 要求鼠标可达，Full 与 Compact 都有 |
| 日志里 | `ForceSent` | `EmittedWhilePaused` |
| 会不会变成习惯 | 会——按一下就过去了 | 不会——它一直挂在那儿提醒你还在旁路里 |

一个临时旁路本来就该长成第二列那样，而不是藏在一个功能键后面。

### 2.3 用模式按钮消错，切中了真实病因

校验失败最常见的原因不是码坏了，是**模式不对**——SKU 模式扫了一个只有 SN 的件。
让工人选模式，正好对着病因。

而且界面必须说清是**在哪个模式下**失败的：只看到一片红，他还得自己回想刚才是什么
模式；看到「在 SKU MODE 下没发出去」，不用想就知道该按哪个按钮。

### 2.4 顺带少两个全局热键

全局热键是系统独占的，注册着的每一个都在别的程序里少一个键可用。现场已经反馈过
F8 冲突，少两个是净收益。

## 3. 规格里哪些条款作废、哪些改写 / What this changes in the spec

| 规格段落 | 处置 |
|---|---|
| **§7 全局控制：F10 强制发送、Esc 取消** | **作废。** 两个热键都不再注册。全程只注册模式切换键一个。 |
| **§7 拦截热键的放行表** | **改写。** 表达它的那段逻辑（`SyncHotkeys`）只剩两种情况：暂停时什么都不注册，其余时间注册切换键。 |
| **§10 强制发送语义 / 取消语义** | **作废。** `ScanProcessor.ForceSend()` 与 `Cancel()` 已删除，`ScanOutcome.ForceSent` / `Cancelled` 已删除，`DiagnosticEventKind.ForceSent` 已删除。 |
| **§10「解析/校验失败进入错误状态并等待 F10 或 Esc」** | **改写。** 失败进入的是一条**提示**，不是等待决定的状态：它不挡住后面的扫码，重扫成功或换模式时自己消失。 |
| **§11.1 错误界面的两个按钮** | **改写。** 「强制发送」「丢弃」换成「切到 SN」「切到 SKU」，另加一块模式徽章。 |
| **§21.9「F10 强制发送与 Esc 取消在错误期间全局可用」** | **作废，由新验收项取代。** 见 §5。 |
| **§5.7 PAUSED** | **完全保留，且分量更重了。** 它现在是原始码进入业务软件的**唯一**通道。 |
| **§8 / §9 解析与校验** | **完全保留。** |
| **§15 诊断日志** | **保留。** 少一种事件（`ForceSent`），其余不变。 |

## 4. 三个子决定 / Three sub-decisions

实施前逐条定下来的：

**① 待决错误不挡住后面的扫码。**
错误是提示不是闸门。挡住的话，工人得先想起来怎么解除——而出错那一刻恰恰最不适合
让人多做一步判断，他此刻只想把手里这件货扫进去。

**② 暂停仍然是「扫什么发什么」，包括解析不了的码。**
这是强制发送的去处，必须写进使用说明，否则遇到怪码的工人会卡在那里。

**③ 换模式清掉提示，但不拿那一枪重发。**
重发看着省一次扫码，但发出去的数据来自换模式**之前**那一枪——工人此刻多半没在
看屏幕，手里的货也未必还是刚才那件。而且扫模式码会变成"有错时顺便发一枪、没错时
只换模式"，同一个动作两种结果。

规则保持一条：**发出去的东西永远对应工人当下这一次扫码。**

---

## 5. 验收项的替换 / The replaced acceptance criterion

§21.9 原文是「F10 强制发送与 Esc 取消在错误期间全局可用」。取而代之：

> **21.9（新）** 解析或校验失败时：不发出任何东西；界面显示失败原因、失败时所处的
> 模式（带模式配色）、以及「切到 SN」「切到 SKU」两个按钮；点任一按钮或扫对应的
> 命令条码都能切换模式并消掉提示，且**不会**重发那一枪；错误期间后续扫码照常处理。
>
> **21.9b** 真正解析不了的码，可以通过暂停原样发进业务软件，且这一枪在日志里记为
> `EmittedWhilePaused`。

## 6. 用例的处置 / What happened to the test cases

- **退役：** `ForceSendWorkflowTests`（FS1~FS15）整个文件删除。
- **退役：** `ScanProcessorTests` 里的 SP10、SP11、SP16、SP17（强制发送与取消）。
- **改写：** SP12「每条输出路径的回车数」从四条路径改成三条——强制发送那条没了，
  而它的能力落在暂停上，暂停本来就是其中一条。
- **新增：** `PendingErrorNoticeTests`（PE1~PE8）。

★ 用例跟着删不是为了让编译通过。它们钉的那件事**不该再发生**——一个还在断言
「规则判定不合格也能原样发出去」的用例，会在有人重新引入这条路径时给出绿灯。

---

## 7. 留下的技术债 / Debt left behind

`Core/Input/` 下这三个文件在本次变更后**完全没有生产代码使用**，只剩它们自己的用例：

- `HotkeyCoordinator.cs`
- `HotkeyConflictDetector.cs`
- `HotkeyRouting.cs`

它们是串口改造之前那套热键路由的遗留，仍然把 F10 / Esc 路由到强制发送与取消。
上线期不做大改动，所以只在文件头加了「死代码」提醒，**没有删除**。

★ 下一个整理周期应当连同用例（HK1~HK14、CO16~CO18）一起删掉。留着一套还在
  描述"F10 → 强制发送"的代码，和本文件第 2 节的结论正面冲突——而冲突的两边
  都在仓库里的时候，后来的人按哪一边做都有理由。
