## 说明 / Notes

「超出回调预算次数」不为 0 是一个预警，不是失败：预算 50 毫秒远低于 LowLevelHooksTimeout 的 300 毫秒。它在告诉你离「Windows 悄悄摘掉钩子」还有多远——而真到那一刻不会有任何通知，进程照跑、界面照显示模式，原始条码却直接流进业务软件（规格 §19.1）。

A non-zero over-budget count is a warning rather than a failure: the 50 ms budget sits well below LowLevelHooksTimeout's 300 ms. It measures how close this is to Windows silently removing the hook — an event that arrives with no notification at all, the process still running and the UI still showing a mode while raw barcodes flow into the business application (spec §19.1).

## 事后说明 / Post-mortem note

**这份报告的「通过」结论是错的，保留它是为了记录这次失败。**
**The "passed" verdict in this report is wrong. It is kept as the record of this failure.**

导出后立刻发现的现象：焦点在诊断工具自己的输入框里一切正常，焦点在其它程序里
则打字与扫码都会冒出一长串重复字符。条码 `DGKJRDC5679F5NF` 扫出来是
`DgkjrcfnDgkjrcfn…` 反复叠加，还有 `打个卡肌肉车`、`日常` 这样的汉字。

根因：**在低层键盘钩子的回调里调用了 SendInput**（补发被扣留的按键）。

1. 回调是同步的，Windows 正等着答复；而把合成按键送进**另一个进程**的输入队列
   （还可能经过它的输入法）会阻塞——本报告里最长一次 3379 毫秒。
2. 超时之后 **Windows 不再理会我们返回的「吞掉」，把按键照常投递出去**，并可能
   把钩子摘掉（规格 §19.1）。
3. 稍后我们又补发了一次 → **同一下按键送达两次**，越积越多，滚成长串。

连带后果解释了这份报告里其余几个数字：回调卡住时消息循环也停了，`WM_INPUT`
排不上队，50 毫秒的关联窗口必然超时，于是每个按键都被判成「来源不明、按普通
键盘补发」——`吞掉 177 = 补发 177`、`处理完成的扫描 0`。扫码枪从头到尾没被
认出来过，它的字符被当成扫描码补发进输入法，于是拼出了汉字。

因此第 5、6、7、9 条**不可能**被验证过（一枪都没处理完），第 2 条也不成立。

### 由此改的三处 / Three changes this produced

1. `DeferredKeyboardOutput`：全部合成输出（补发与文本）排进同一个队列，由消息
   循环发送。**钩子回调里一个字节都不往外发**，只排队并投递一条消息。
2. `GateChecklist.FindContradictions`：报告不再签发与自己的运行时计数矛盾的
   结论。一个会在自己的数据面前签发相反结论的关卡，等于没有关卡。
3. 文件头记录了这次事故，免得日后有人把 SendInput 挪回回调里。
